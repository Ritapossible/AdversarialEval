# Independent software and code verification for Qwen (plan, 25 Nov 2026)

Source: Telegraph's "Alibaba: Commercial Applications" thread, item 4, **Independent Software &
Code Verification (Qwen / Alibaba Cloud)**, assigned to this project. Earlier guidance from the
same thread owner (24 Nov DM): a verification layer before AI-generated software reaches
production, with authoritative sources, Telegraph receipts, real results and a short video.

> Build an independent verification layer for software generated by Qwen and other AI models.
> Investigate package authenticity, dependencies, vulnerabilities, insecure implementations, API
> compatibility and whether generated code actually fulfils the original requirements. Rather than
> simply asking another model to review the code, use specialist intelligence, official
> registries, deterministic checks and actual execution results. ... difficult test cases
> comparing Qwen alone against Qwen combined with Telegraph, measuring correctness, security,
> completeness, cost and latency.

Status: **planned.** Blocked on Qwen API access (see the end).

## The product: Dependency.Guard, extended from dependencies to the whole change

Input: a task description and the code Qwen generated for it (files plus a lockfile or manifest).
Output: **DEPLOY** or **HOLD**, with one evidence line per check, every source linked and every
paid answer's receipt.

| Ahmed's check | How it is established (not by asking another model) | Status |
|---|---|---|
| Package authenticity | the registry itself: the name and version were published, aren't withdrawn malware, aren't a near-miss of a popular name (OSV `MAL-`, npm/PyPI history) | **built** (Verified Ask) |
| Dependencies | the lockfile's resolved versions, including transitive ones | **built** (connector reads lockfiles) |
| Vulnerabilities | OSV per exact version, plus Telegraph's `SECURITY_REVIEW` answer checked against it | **built** |
| Does a reported vulnerability actually affect this code? | static reachability: is the advisory's vulnerable function imported and called? (OSV `affected[].ecosystem_specific` symbols where present, else the advisory text's function names) | new |
| Insecure implementations | deterministic scanners (Semgrep rules, Bandit for Python) for known insecure patterns, with Telegraph's code-review answers checked against them | new |
| API compatibility | install the exact locked versions in a sandbox, then import and type-check (Python import plus mypy/pyright, TypeScript `tsc`): a call to a function or parameter that doesn't exist in that version fails | new |
| Fulfils the requirements | hidden acceptance tests written before generation, run in the sandbox | new |
| Fix verification | apply the proposed fix (upgrade or patch), re-run every check and the tests: the fix must close the issue without breaking anything | new |

Telegraph's part: specialist answers bought per check (`SECURITY_REVIEW_GENERAL`; also
`CODE_PATCH_VERIFY_GENERAL` and any code intent the listing shows on the day), each checked against
the deterministic evidence before it counts, as Dependency.Guard does today.

## The comparison (pre-registered before any generation or paid call)

**Tasks.** About 12 small but realistic tasks, written by rule and frozen with their hidden
acceptance tests, chosen where AI-generated code is known to go wrong:
- a dependency choice where the obvious version is vulnerable or withdrawn;
- a package name models are known to invent (a near-miss that doesn't exist or is malware);
- an API that changed between major versions (the generated call doesn't exist in the locked version);
- insecure defaults: `yaml.load`, `shell=True`, JWT without algorithm pinning, SQL string building,
  path joins with user input, disabled TLS verification;
- requirements with an edge case the tests check (empty input, unicode, limits).

**Arms**, all on the same generated code where possible:

| Arm | Decides DEPLOY or HOLD from |
|---|---|
| A. Qwen alone | Qwen generates the code, then Qwen reviews its own code and decides |
| B. Qwen + Telegraph, trusted | Telegraph's specialist answers, acted on as returned |
| C. Qwen + Dependency.Guard | Telegraph answers checked against registries, OSV, scanners, type checks and the hidden tests |

**Truth.** A change should be HELD if any hidden test fails, a dependency is vulnerable in a
reachable way, withdrawn or non-existent, or an insecure pattern is present; otherwise DEPLOY.
Truth comes from execution and public sources, fixed before any arm runs.

**Measured** (per Ahmed): correctness (right DEPLOY/HOLD), security (unsafe changes let through),
completeness (requirements met, from the hidden tests), cost (Qwen tokens and Telegraph receipts,
reconciled), latency. Wilson intervals; limits stated in advance.

## Deliverables

- Report with the three arms, per-check evidence and receipts, signed like the rest.
- A demo video (about 2 minutes): one Qwen-generated change that Qwen approved and Dependency.Guard
  held, with the evidence and the fix it verified.
- A website section on the Dependency.Guard page; a post in the thread, tagging the owner.

## Order of work

1. Qwen access confirmed (model id, endpoint, price) and a smoke call.
2. Tasks, hidden tests and rule committed (frozen).
3. Sandbox checks built and unit-tested: install-and-import, type check, scanners, reachability, tests.
4. Generate with Qwen; run arms A, B, C; reconcile costs.
5. Report, signing, site, video, thread post.

## What we will not claim

- Nothing about Qwen beyond the tasks tested; the task set is small and chosen to be hard.
- Arm A uses Qwen's own review; another model could do better or worse.
- Execution runs in a sandbox with the locked versions; production environments can differ.
