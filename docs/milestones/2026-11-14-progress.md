/progress AdversarialEval: SECURITY_REVIEW Evaluator adapter + adversarial preference data

Repo: https://github.com/Ritapossible/AdversarialEval

**Working now**
- End-to-end pipeline on the unmodified kit (pinned `1ed063e`): verified data → `train_adapter` → `export_adapter` → the node's own Stage 1 check (`adapterbuild.CheckLoRA`) passes for our packages (rank 8 and rank 16).
- Local dress rehearsal of the node's remote check: our package served by the kit's `adapterexec` on the real foundation graph and WASM engine, called through the node's own client (`pkg/wasm/remote`). The identity echo works, and a wrong adapter hash is rejected exactly as the node does. The WASM engine and our PyTorch scoring order 87/87 validation pairs identically (max score diff 8e-5).
- Data: 264 training pairs + 87 held-out validation pairs. Of these, 194 are minimal pairs generated from OSV, each differing in one decisive fact, with every label re-checked by OSV's own version query. The kit's dataset gate passes; every naive scorer (longer/shorter wins, keyword overlap, hedging, id count) stays ≤ 58%.
- Results so far (validation only, our own authoring, 2 seeds each): ~72–74% pairwise accuracy. Hand-written pairs 77–85%, generated minimal pairs 67–69%.

**Findings worth sharing**
- Minimal pairs exposed a "polarity shortcut": a model trained on hand-written data scored 100% when the right answer was "affected" and 0% when it was "patched". It was picking the vulnerable-sounding answer. Balanced minimal pairs broke it, and this replicates across seeds.
- A 15-pair remote check is very noisy. At a true 75% accuracy it passes only ~69% of the time (binomial; needs 11/15). Our own rehearsal passed 4 of 6 draws with the same adapter.
- Kit issues found while integrating, with tested patches ready to share: tokenizer file-hash mismatch between HF and the pinned tokenizer (same ids), the offline `adapterbuild` class check, a `NameError` after a passing gate, and non-deterministic export bytes (metadata key order).
