# Qwen alone vs Qwen + Telegraph: independent verification of Qwen-written code (2026-11-28)

Item 4 of Telegraph's Alibaba thread: an independent verification layer for software generated by
Qwen, comparing Qwen alone against Qwen combined with Telegraph on correctness, security,
completeness, cost and latency.

**Pre-registered** in `codeverify/RULE.md`, committed in `68c0dfa` before Qwen wrote any code.
Amendment 1 (`7647c69`) fixed my reply parser before any review, check or paid call. It changed
no outcome: replies were re-read, not regenerated. Raw data are in `bench/out/codeverify/`.

**Model.** Qwen2.5-Coder-7B-Instruct, Alibaba's open-weight coding model, run locally:
- quantisation Q4_K_M, llama.cpp, 4 CPU threads;
- file SHA-256 `509287f7…894d3c`, matching Hugging Face.

It is not Qwen's API: no Alibaba Cloud key could be opened. Nothing here is claimed about larger
Qwen models.

**What was tested.**
- 12 everyday tasks, each with a known way to go wrong: YAML loading, shell commands, JWT checks,
  SQL, file paths, archive extraction, password storage, a removed pandas API, HTTP and
  dependency pins, UTF-8, input validation, XML.
- 3 samples each, so 36 changes.
- Each task has visible tests (the customer's acceptance tests) and hidden tests (used only for
  truth). A correct and an unsafe reference solution per task checked the tests first: all 12
  correct ones pass, and all 12 unsafe ones are caught.

**Truth** comes from execution and public sources only: a real install on Python 3.12, PyPI,
OSV, and the visible and hidden tests. No model decides it.

## Result

| Arm | Decides from | Correct (of 36) | Wilson 95% | Unsafe or broken changes let through | Good changes blocked |
|---|---|---|---|---|---|
| A. Qwen alone | Qwen reviews its own change | **6** (17%) | 8–32% | **30 of 30** | 0 |
| B. Qwen + Telegraph, trusted | Telegraph code review + dependency answers, as returned | **14** (39%) | 25–55% | **22** | 0 |
| C. Qwen + Dependency.Guard | Telegraph answers checked; PyPI, OSV, real install, import, visible tests, Bandit | **27** (75%) | 59–86% | **9** | **0** |

**Completeness.** 6 of the 36 changes are correct and safe (17%, Wilson 8 to 32%). 30 should not
reach production.

**Qwen alone approved all 36 of its own changes,** including:
- code that crashes on every input;
- a password store using plain SHA-256;
- a dependency version that doesn't exist.

## What all three missed (9 changes, found only by the hidden tests)

- **Path traversal in `read_upload` (3 of 3 samples).** It reads `../secret.txt` from outside the
  upload folder. Bandit has no rule for it, and the visible tests don't try it.
- **Unsalted SHA-256 passwords (1).** Bandit only flags MD5 and SHA-1.
- **Duration parser accepts `30m1h` and `1h1h` (3).**
- **UTF-8 truncation cuts an emoji in half (1).**
- **pandas `add_row` keeps the old index (1).**

These are the limits of static scanners plus the customer's own tests. They're why
Dependency.Guard reports its evidence instead of claiming code is safe. The fix: ask the customer
for the abuse cases (`../`, wrong order, emoji) as acceptance tests, and add a path-traversal and
password-hashing rule. Both are planned, not claimed.

## Telegraph's answers (arm B), checked

All 45 questions were paid on Solana devnet, x402 routed at $0.01 each. All 45 payments were
confirmed on-chain: **$0.45** (`telegraph/onchain.json`). One answer was lost to a network error
after its payment settled; it is counted, as in the 24 Nov Solana run.

**Code review (`CODE_REVIEW_GENERAL`, 36 changes, all answered by Telegraph Sentinel Risk
Intelligence):**
- 34 verdicts are **Approve**; 1 has no verdict, and 1 answer was lost.
- 29 of the 35 summaries describe a problem, yet the verdict is Approve every time. Those 29
  include 24 changes that should be held and 5 of the 6 good ones.
- Some summaries are right. For `read_upload` the reviewer names the path traversal ("CWE-22"),
  and for the duration parser the missing order check.
- Others describe code that isn't there (a regex JSON extractor in a change with no regex).
- So neither the verdict nor the summary can be used to decide on its own. Dependency.Guard keeps
  the review as evidence but doesn't hold on it.

**Dependency security (`SECURITY_REVIEW_GENERAL`, 9 pins, answered by TxLens):** none could be
verified by Verified Ask.
- **"Secure" for PyJWT 2.6.0 and 2.7.0:** OSV lists 14 advisories each. Contradicted.
- **"Secure" for `passlib==1.9.6`:** that version doesn't exist. Contradicted.
- **"Insecure" for pandas 2.2.0:** OSV lists none. Contradicted. Arm B's three pandas holds were
  right only because Qwen's code was broken for another reason.
- **"Insecure" for requests 2.28.2 and lxml 4.9.3:** correct, but no advisory was cited, so these
  stay unconfirmed.

This is why arm C checks every paid answer before it counts. Taken as returned, Telegraph's answers
improved on Qwen alone (14 vs 6 correct), but they let 22 unsafe or broken changes through.

## Fix verification (secondary)

Qwen got Dependency.Guard's findings for each of the 21 changes it held, and one try to fix them
(temperature 0, `fixes/`, `fix_checks.jsonl`):

- **1 of 21 fixes reaches truth DEPLOY.** Qwen removed the stray `requirements.txt` line.
- **19 fixes return the same code and pins unchanged.** For example, Qwen keeps `PyJWT==2.7.0` after
  being told it has 14 OSV advisories, and keeps the crashing `extract_archive`.
- **1 fix makes it worse.** It declares the missing `bcrypt`, but as `bcrypt==5.1.3`, a version
  that doesn't exist.
- **Dependency.Guard's checks agree with the truth on all 21 fixes.** No broken fix would have
  been deployed.

For this 7B model, a review loop with its own findings doesn't fix much. The checks matter
because the model doesn't correct itself. One fair point against us: our finding lists the
advisory IDs but not the safe version to move to. Naming the fixed version in each finding is the
next improvement.

## Cost and latency

| | Qwen alone | + Telegraph (trusted) | + Dependency.Guard |
|---|---|---|---|
| Telegraph spend | $0 | $0.45 for 36 changes (1.25¢ each) | the same paid answers, plus free checks |
| Time per decision (median) | 32 s (local CPU review) | 25 s per paid answer | about 20 s of checks per change (install, tests, OSV) |

Qwen ran locally at no charge: 36 generations in 20 minutes, median 32 s each.

## Limits (stated in advance)

- 36 changes from one 7B model at 4-bit on CPU, and 12 tasks chosen to be hard. A larger Qwen
  model may write safer code.
- Arm A is Qwen reviewing itself; another reviewer could do better or worse.
- Truth and arm C share the dependency and install checks (PyPI, OSV, a real install). C's
  advantage on those rows comes from running them at all, which A and B don't. C never saw the
  hidden tests.
- One day's OSV data. Python 3.12 on Linux.
