## Correction and key finding (added 2026-11-11)

**Correction:** this run trained on the **95** hand-written pairs (`runs/frozen/train-95.jsonl`). The
generated pairs didn't exist when it started. The "Train: 252 pairs" header and the 71.4%
"train" score above are wrong: `train.sh` re-scored against the rebuilt 252-pair file. Of
those, 157 pairs were **never seen** by this model. `train.sh` now pins and snapshots the
training file per run.

**Seed variance (U4):** with an identical config, seed 13 scored 76.9% (early stop kept epoch 3)
and seed 7 scored **87.2%** (95% CI 73.3–94.4%; all 6 epochs, validation loss still falling).
That's about 10 points between seeds, so single-run numbers are not decision-grade.

**Key finding: a polarity shortcut that the hand-written validation set hides.** On the 157
unseen pairs:

| subset | n | accuracy |
|---|---|---|
| seen (95 hand-written) | 95 | 97.9% |
| unseen targeted (batch E) | 11 | 72.7% |
| unseen generated, all | 146 | 54.1% |
| ↳ F2-in (right answer: *affected*) | 45 | **100%** |
| ↳ F2-out (right answer: *patched*) | 42 | **0%** |
| ↳ F1 / F7 / F8 | 24 / 23 / 12 | 62.5% / 52.2% / 58.3% |

The adapter hasn't learned version comparison, even when the prompt quotes the affected
range. It learned "the answer that says *vulnerable* wins". On the hand-written validation
pairs its F2 accuracy is 100%, because style differences there give it other cues. The
minimal pairs remove those cues and expose the shortcut. This is the measurement gap
AdversarialEval targets, found in our own model. From now on every run is also scored on a
**held-out generated minimal-pair set** drawn from packages that training never sees.
